## 1. 项目背景与目标

### 1.1 背景

【已确认】建设面向企业数据集成的 ETL-Agent 控制面平台，将自然语言需求转换为经过校验、版本冻结、独立审批和受管执行的数据集成任务，并提供质量分流、运行监督、审计与评测闭环。

【暂定假设】从原文功能范围推导，目标问题包括：异构数据接入与映射准备成本高；自然语言生成结果难以直接信任；审批内容与实际执行内容可能脱节；数据发布失败后缺少明确恢复路径；安全能力缺少可重复评测证据。这些痛点尚未经过用户访谈或量化验证。

### 1.2 目标

1. 支持从受管数据源与元数据 Profile 出发生成可审查的 ETL 方案。
2. 确保实际执行与已冻结、已审批事实一致，阻止自批、越权、重放及绕过安全出口的执行。
3. 将有效数据与错误数据分流，满足质量条件后发布，并支持异常诊断与受管回滚。
4. 保留从业务需求到制品、审批、运行、质量报告的证据链。
5. 交付可运行系统、示例数据、Benchmark 与完整业务演示。

成功判断以第 12 节验收为准。原文没有给出节省工时比例、吞吐目标、可用性 SLA 等数字，本稿不编造这些指标。

## 2. 目标用户和用户痛点

| 目标用户（已确认） | 工作目标 | 痛点推导（暂定假设） |
|---|---|---|
| 数据工程师 / Maker | 接入数据、生成与调试方案、提交版本和审批 | 字段映射、配置生成和修复步骤繁琐，缺少可复现版本 |
| 数据审批人 / Checker 1 | 核查业务口径、字段映射、质量规则与 DAG | 难以确认实际执行是否与审批内容一致 |
| 安全审批人 / Checker 2 | 核查资源、敏感等级、预算、凭据引用与回滚 | 难以判断生成配置是否越权或超出风险边界 |
| 系统操作员 | 在审批完成后提交执行，监督、取消和回滚 | 失败定位、重复执行防护及发布恢复不够明确 |
| 审计人员 | 检查历史、证据账本、质量和评测报告 | 缺少完整、可验证且能检测篡改的过程证据 |

## 3. 产品范围与非目标

### 3.1 本期基线范围（已确认）

- 用户认证、多租户项目、成员与角色、敏感凭据受管存储。
- 数据库、文件、对象存储及 REST API 接入，安全元数据探查与脱敏样本。
- 自然语言澄清、可恢复生成流程、多模型适配、EtlPlan/HOCON 生成与确定性校验、有限修复。
- 不可变版本、差异查看、准备单、风险分级、独立审批、单次能力授权、可靠异步执行。
- 影子表写入、错误分流、质量检查、原子发布、预算监督、暂停/取消/回滚、安全重跑。
- 运行中心、证据账本、Benchmark、安全进化和交付演示。

原文列出的接入类型均保留在范围内；不能因为演示使用 MySQL→Doris，就把其余接入类型默认为已取消。各类型的源端/目标端能力及首期覆盖以 Q-02 决策为准。

### 3.2 非目标及范围限制

- 不引入其他章节的舆情分析、经营归因、客服、知识库或模型微调业务。
- 不扩展为通用 BI、数据可视化分析、任意命令执行或自动业务决策平台。
- 不承诺未经列明的数据源、写入模式、CDC/实时同步、跨系统分布式原子事务或完整数据目录产品。
- 不把 Agent 的建议等同于审批，也不赋予其自行修改安全策略并直接投入正式执行的权限。
- 本文不新增 API 路由、数据库字段、框架、算法或部署拓扑设计；第 13 节仅保留原文已有技术约束及契约位置。

| REQ-018 | 独立审批：数据与安全审批人审查冻结事实，具名同意或拒绝，展示决策状态。 | AC-018：审批对象准确指向准备单与版本；只完成一个必需审批不能 Commit；任一必需审批拒绝后不能 Commit；两个独立必需审批完成后可进入提交校验。撤回/过期规则待 Q-07。 |

| REQ-020 | 单次能力与唯一副作用出口：使用 Ed25519 签名 Capability，绑定工具、主体、环境、制品指纹，有效期 5 分钟；统一出口校验并防重放。 | AC-020：有效且未消费令牌可被消费一次；第二次消费、过期、篡改、绑定不匹配及绕过出口调用均被拒绝；并发消费最多一项被接受。5 分钟从签发起算及消费节点按 ASM-04/Q-09 确认。 |

### 6.5 异步执行与调度

| 编号 | 功能与产品行为 | 可验证验收条件 |
|---|---|---|
| REQ-021 | 可靠提交与投递：运行事实与 Outbox 命令原子保存，支持异步交付执行。 | AC-021：模拟提交中断，不能出现仅有可执行命令却无关联运行的半提交；模拟投递暂时失败，恢复后可查投递结果。重复交付不能产生第二个逻辑运行；引擎侧去重边界见 Q-09。 |

## 7. 核心用户场景与业务流程

### 7.1 场景一：MySQL→Doris 受管集成（原文明示）

1. Maker 在项目内登记源、目标连接，完成测试和 Profile 探查。
2. 在 Studio 输入需求，选择 Profile；必要信息缺失则进入澄清，回答后恢复。
3. 生成 EtlPlan、HOCON、DAG、字段映射和质量契约；执行确定性门禁及有限修复。
4. 试运行仅按 Q-10 确认后的模式执行；有副作用时使用独立受管授权，不先行写入生产目标。
5. 通过门禁后冻结版本，生成摘要；Prepare 冻结影响范围、预算和回滚事实。
6. 数据审批人与安全审批人完成独立审批；拒绝或事实变化则不能继续提交。
7. 操作员 Commit，服务端复核后签发/验证单次授权并可靠创建执行。
8. Worker 调用 SeaTunnel；有效数据入影子表，违规数据入错误表，持续监督预算。
9. 质量通过后原子发布；否则保持未发布并进入异常处理。
10. 查询运行、质量报告及证据链。

### 7.2 场景二：异常诊断与安全恢复（原文明示）

发生执行异常或预算超限 → 记录监督/失败快照 → 按策略中断或告警 → 展示证据、诊断和建议 → 操作员发起受管回滚/清理 → 校验恢复结果 → 如需重跑，按新运行授权流程执行。

不能把取消成功、搬运成功、质量通过、发布成功、回滚成功合并成同一个结果。它们分别描述不同业务事实。

### 7.3 状态语义草案（ASM-07，状态名及转换待评审）

| 对象 | 建议状态语义 | 不允许的混淆 |
|---|---|---|
| 生成工作流 | 进行中、待澄清、校验中、修复中、完成、失败 | 完成生成不代表完成数据执行 |
| 版本 | 可编辑候选、冻结版本 | 修改冻结版本应形成新版本 |
| 准备/审批 | 待审批、审批满足、已拒绝、事实失效、已提交 | 已审批不能覆盖后续指纹变化 |
| 执行 | 待调度、运行中、取消请求中、已取消、失败、成功 | 取消请求中不代表引擎停止 |
| 发布 | 未发布、待质量判断、发布中、已发布、发布失败 | 数据搬运成功不等于已发布 |
| 回滚 | 未请求、进行中、成功、失败 | 回滚失败不能标记业务数据已恢复 |

暂停相关转换、崩溃恢复、终态修正规则须依 Q-09/Q-13/Q-15 决定，本表不规定数据库枚举。

## 13. 依赖、风险和限制

### 13.1 既有技术与接口约束

以下技术来自原文，属于已给定约束而非本文新增选型；具体版本、配置、实现结构由后续技术设计确定。

| 原文既有约束 | 产品影响 |
|---|---|
| Vue 前端；FastAPI 控制面 | 提供原文列明的控制台与受保护服务入口 |
| LangGraph 与 PostgreSQL Checkpoint | 支持生成状态机中断及跨请求恢复 |
| Celery Worker/Beat、PostgreSQL、Redis | 支持异步执行、调度与控制事实持久化 |
| Apache SeaTunnel Zeta、HOCON | 数据面负责实际搬运，生成结果需与执行引擎兼容 |
| SecretProvider / Vault KV v2 | 凭据以受管引用使用；具体部署形态待确定 |
| PDP、P0—P3、Ed25519、5 分钟单次 Capability、Replay Guard、Tool Broker | 固定安全能力基线，产品不能放开旁路 |
| 事务 Outbox、哈希链和签名检查点 | 支撑可靠提交与可验证证据，仍需故障恢复/检查点策略 |
| Doris 原子 Swap 示例 | 至少演示已给出的原子发布路径；不能外推所有目标端都支持 |

接口以原文 2.8.8 为既有基线：健康（REQ-036）、连接/测试/Profile（REQ-005/006）、文件（REQ-007）、Pipeline/生成/回答/设计（REQ-008—REQ-011）、准备/审批/Commit（REQ-016—REQ-020）、运行查询/取消/回滚（REQ-029/030/032）、Benchmark（REQ-038）。原文没有完整列出认证、项目授权、暂停、调度、安全重跑及进化管理接口，后续需补充接口设计，不在本 PRD 擅自规定路由。

### 13.2 外部依赖与主要风险

- 数据源权限、网络、驱动/连接器和目标端能力影响接入与执行范围；需连接能力矩阵，不把“可连接”当作“支持所有写入模式”。
- 模型服务可能超时、不可用或生成错误；确定性门禁及有限修复必须独立于模型判断。
- 审批人、风险策略和质量口径未配置时，端到端执行链路无法获得完整验收依据。
- 多租户主体未在原文数据表中明示，不能仅以项目字段声称完成全部租户隔离。
- 凭据轮转、源 Schema 变化和目标数据变化可能使准备事实过期，须定义指纹覆盖范围。
- Outbox 只能保证本地原子提交，仍存在引擎启动后回执丢失的重复执行风险。
- 错误表保留原始值与“全链路无敏感明文泄露”存在边界冲突，需确定受保护存储及查看政策。
- 回滚依赖目标端能力、旧版本保留及并发写入控制；清理后未必可以恢复。
- Benchmark 准确率和拦截率缺少基准集及阈值时，只能证明“有评测输出”，不能证明达到安全或准确性目标。
- 本稿没有提供未经讨论的发布日期、成本预算、开发周期或团队规模。
